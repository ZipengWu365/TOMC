# 按成本决定的网关压缩

[English](compaction_policy.md) · [上下文归属](context_ownership_zh.md) · [提示词缓存](prompt_cache_20261017_zh.md)

请求网关只有在预计"改写后比原样发送更便宜"时，才会改写请求。Claude、Codex 和 OpenAI 兼容的 Chat Completions（`openai`）三条路由的默认策略都是 `policy="dynamic"`。`policy="legacy"` 保留旧行为：只要大小条件满足就压缩。

## 为什么压缩可能亏钱

提供商对重复出现的请求开头按缓存价计费。以 Claude Sonnet 5.5 为例，价目表中每百万 token 的价格是：

| 类型 | 价格 |
|---|---:|
| 普通输入 | 2 美元 |
| 缓存读取 | 0.1 美元 |
| 1 小时缓存写入 | 4 美元 |

写入一次的价钱等于读取 40 次。

改写会让请求从第一个被改动的消息开始，往后的内容全部重新写入缓存。而被删掉的历史，本来在之后每个请求里只按 0.1 美元每百万 token 的价格从缓存读取。

用 Claude Code 跑的 50 道 SWE-bench Verified 题里，旧的当前轮压缩只要触发就亏钱：

- 29 次重建多花了 0.73 美元；
- 之后 152 个复用请求一共只省下 0.105 美元。

每次重建要约 36 个后续请求才能回本，而短任务平均只剩约 5 个。另外，每新增 6K token 就从同一锚点重来一次，导致重写量越来越大。

## 决策

每个候选改写都和原样发送比较。计算方式见 [`compaction_policy.decide`](https://github.com/ZipengWu365/TOMC/blob/main/src/tomc/compaction_policy.py)：

```
立即成本 = 现在改写的费用 − 现在原样发送的费用            # 缓存写入 vs 读取
未来收益 = 缓存读取价 × 删掉的 token × (1 − 风险) × 预计剩余请求数
重读成本 = 风险 × 删掉的 token × 写入价
当 未来收益 − 立即成本 − 重读成本 > margin × (max(立即成本, 0) + 重读成本) 时才压缩
```

各项输入这样估计：

- **价格：** 按请求里的模型从内置或已同步的价目表读取。宿主把缓存标成 `ttl: "1h"` 时用 1 小时写入价。未知模型用保守的默认值。
- **缓存冷热：** 上一个请求距今不到缓存有效期的 90%，并且它的大请求确实命中了缓存，就算"热"。缓存是冷的时候（第一个请求、已过期、提供商不做缓存），整个请求本来就要全价计费，缩短请求立刻省钱。
- **预计剩余请求：** 取这台机器上同一宿主、曾经跑到同样长度的历史会话，看它们之后还跑了多少，取中位数。这类会话不足 8 个时，按"已经跑过的一半"估计。
- **风险：** 被压掉的工具调用，之后又被模型原样重新调用的比例，初始先验为十分之一。读同一个文件，不管读的是哪几行，都算重复。
- **窗口压力：** 请求达到模型官方窗口的 80% 时一定压缩，这比让宿主用大模型写摘要便宜。

## 改写方式

两条路由都会把改写后的前缀存在网关本地，并在之后的工具步和用户轮次里一字不差地复用，保证缓存持续命中。

**第一次压缩：** 保留第一个工具结果原样。在 Claude 里是 `tool_result` 消息，在 Codex 里是字符串形式的 `function_call_output`。没有工具调用的纯聊天，则保留第一条用户消息。从它之后到最近几条之间的内容被压缩，记忆附加在这条保留的消息里。

**之后的压缩：** 只压缩冻结前缀之后新增的部分，新记忆附加到冻结前缀里最后一条载体消息上，之前的记忆保持不变。所以缓存仍然能命中到那条载体消息为止。

**宿主的系统提示：** 宿主每一步插入的系统提示（比如工作目录更新、进度提醒）会作为标注过的宿主数据一起压缩。只带 `output_config`、内容为空的控制消息原样保留。其他系统消息会让分段在它之前结束。所有留下来的系统消息后面仍然紧跟一条 assistant 消息。

**Codex：** reasoning 项和它后面的那组调用一起删掉。调用和它的输出（包括并行调用）不会被拆开。遇到指令、宿主上下文、设置项或压缩状态，分段就在它之前结束。

**Chat Completions（`openai` 路由）：** 适用于任何 OpenAI 兼容的 `/chat/completions` 上游。客户端用 `x-tomc-session-id` 请求头标明会话，这个头不会转发给上游；没有这个头的请求原样放行。assistant 的 `tool_calls` 和它对应的所有 `tool` 结果不会被拆开，记忆附加在一条工具结果里。

**始终原样发送的部分：** 最新的用户问题和最近几条消息。

## 配置

以下键写在网关配置的 `compression` 里，也可以按路由单独设置：

| 键 | 默认值 | 含义 |
|---|---|---|
| `policy` | `dynamic` | `dynamic` 或 `legacy` |
| `objective` | `cost` | `cost` 按账单计（缓存读取按折扣价）；`tokens` 每个输入 token 一样算，适合有 token 配额、每分钟 token 限额或订阅用量限制的情况 |
| `margin` | `0.5` | 净节省至少要达到有风险成本的多少倍 |
| `window_pressure` | `0.8` | 达到窗口的这个比例时强制压缩 |
| `remaining_prior` | `0.5` | 没有历史会话时，按"已跑请求数 × 该值"估计剩余请求 |
| `turn_memory_ratio` | `0.35` | 记忆预算占被压缩分段的比例 |
| `recent_messages`、`min_history_tokens`、`memory_budget` | 同旧版 | 保留的最近消息数、分段最小长度、固定预算 |

`turn_trigger_tokens` 和 `turn_regrow_tokens` 只在 `legacy` 下生效。

活动记录只存决策用到的数字，不存任何内容：

- `policy`：`profitable`、`cold_cache`、`window_pressure` 或 `unprofitable` 之一；
- `policy_gain` 和 `policy_cost`，单位是按普通输入价折算的 token；
- `policy_remaining`；
- `policy_warm`。

网关还会把每次响应里提供商报告的用量写回会话账本，用来更新缓存冷热和 token 换算比例。

## 证据与局限

用 50 道题录下的每个请求的大小离线重放这套决策，这是一个离线估计：

- 有 113 个请求的可压缩内容在 4K token 以上；
- 动态策略一个都没有压缩。

在 Anthropic 1 小时缓存的价格下，缓存热的时候压缩，只有在还会持续很久的长会话里才划算。此外，在缓存已冷的时候（比如超过缓存有效期后恢复会话），以及接近模型窗口时，压缩也划算。

剩余请求数的估计是启发式的。缓存最多 4 个断点、最多回看 20 个块的规则，这里用"保留前缀"做近似，没有精确建模。压缩对任务质量的影响还需要实测。
